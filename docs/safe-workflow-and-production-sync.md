# Безпечна робота з TechnoSAP через GitHub

## Межі цього етапу

Production не розгортати. Цей PR додає лише CI та план роботи.
Наявний draft PR #1 не є підтвердженням відповідності поточному production.
Не зливати його до завершення порівняння з production.

На момент підготовки:
- main: 8ccd87b127e9a6ccc8a268b9f171f39cd602dd7c (каркас застосунку).
- agent/mobitime-import-mvp: 9654316d6cecae773a958302296d9f172b4161a2.
- PR #1 згадує історичний production commit 3fdc4139590fedcc7dba7cab70aa4dced258aaed.
  Поточний сервер, образ та локальні зміни ще не перевірені.

## Щоденний процес

1. Окрема гілка для кожної зміни; спочатку draft PR.
2. Перегляд diff та успішний CI перед злиттям.
3. CI виконує перевірку синтаксису Python та standalone unittest на Python 3.11.
   Він не перевіряє роботу всередині ERPNext, базу даних або міграції.
4. Зміни DocType, облікових документів та міграцій додатково перевіряти
   у відокремленому staging із безпечно підготовленими тестовими даними.
5. Деплой — окремий майбутній процес після перевіреної синхронізації
   та окремого дозволу власника.

CI використовує GitHub-hosted runner, лише contents: read, без production secrets
і без SSH. Checkout не зберігає облікові дані. Actions закріплені на commit SHA.
Не додавати pull_request_target для виконання коду PR.

## Захист main — ще потрібно налаштувати власнику

Після першого успішного запуску CI увімкнути branch rule/ruleset:
- вимагати pull request перед злиттям;
- вимагати успішну перевірку Python smoke tests (обрати фактичний check у GitHub);
- заборонити force push та видалення main;
- обмежити обхід правил.

Цей документ не встановлює ці правила. Для одноосібної роботи не вимагати
схвалення від іншого reviewer, якщо такого reviewer немає.
Перед увімкненням перевірити доступність правил для тарифу та репозиторію.

## Одноразова синхронізація production → GitHub

### 1. Встановити джерело істини, нічого не змінюючи на сервері

Власник повідомляє спосіб запуску (Docker Compose чи bench), шлях застосунку
та спосіб доступу. Паролі, токени, приватні ключі й site_config.json у чат
або репозиторій не передавати.

У погодженому терміналі спершу зібрати лише метадані:
- версії Frappe, ERPNext та встановленого застосунку;
- поточний image ID/digest і commit застосунку;
- git status, перелік змінених та untracked файлів;
- наявність bind mounts: код у контейнері може відрізнятися від образу.

Не виводити повні environment/configuration dumps: вони можуть містити secrets.
Якщо .git відсутній, зробити інвентаризацію вихідних файлів із контрольними сумами.
Зафіксувати час знімка та джерело. На час знімка погодити паузу ручних змін коду.

### 2. Зберегти можливість відновлення

Перевірити наявність актуальної резервної копії бази та private/public files
у закритому сховищі, її цілісність і відновлення в ізольованому середовищі.
Зафіксувати поточний образ/digest і конфігурацію запуску в захищеному місці.
Жодних резервних копій або конфігурацій із секретами в GitHub.

### 3. Підготувати чистий знімок коду

Скопіювати лише код supplier_invoice_importer у захищений staging-каталог,
не змінюючи production. Зберегти незакомічені зміни коду.
Не копіювати .env, site_config.json, common_site_config.json, ключі,
бази, backups, logs, uploads, клієнтські Excel-файли чи каталоги sites.

Перевірити список файлів, diff і вміст на секрети та персональні дані
до будь-якого push. Репозиторій публічний.
Зафіксувати commit/image digest та контрольні суми як походження знімка.

### 4. Порівняти та оформити PR

Створити production-sync/YYYY-MM-DD від актуального main.
Порівняти знімок із main та agent/mobitime-import-mvp:
- що є на production;
- що є лише у PR #1;
- що відрізняється або видалене.

Перенести лише перевірені вихідні файли, зберігши CI та документацію.
Список видалень переглянути явно; не застосовувати сліпе очищення.
Відкрити draft PR з походженням знімка, переліком змін та результатами тестів.
Жодних git pull/reset, bench migrate/build/restart або зміни образу на production.

### 5. Завершення

Після CI, staging-перевірки та перегляду власником злити знімок у main.
PR #1 окремо перебазувати/скоригувати або закрити відповідно до порівняння.
Злиття цього знімка не повинно запускати деплой.
Лише після цього проєктувати окремий ручний deployment із backup,
контрольованими міграціями та перевіреним планом відновлення.

## Критерій готовності

GitHub містить перевірений знімок поточного production-коду з відомим
походженням; CI зелений; правила main увімкнені; невідповідності PR #1
розібрані. До виконання цих пунктів синхронізація не вважається завершеною.
